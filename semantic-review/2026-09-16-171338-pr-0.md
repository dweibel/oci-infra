# Federated OKF and Hermes companion architecture alignment

The documents define a Git-canonical, SQLite-first knowledge federation with separate Hermes memory, shared TypeScript/Go adapters, and distinct project and ecosystem evidence scopes. Four publication-blocking gaps remain: Hermes integration artifacts have no repository owner, ecosystem verification has no execution path, receipt signing sits on an undefined trust boundary, and index regeneration lacks a role and review policy. Independent implementations could therefore place durable assets inconsistently, claim completion without required E2E execution, or give the client-facing MCP service unintended signing and write authority.

Watch for: **confirmed** unassigned ownership for the Hermes profile and skill; **confirmed** missing ecosystem-orchestrator workflow; **confirmed** ambiguous MCP receipt-attestation authority; **confirmed** unscoped canonical index regeneration.

**Verdict**: NEEDS_CHANGES

## High-level view

The parent assigns project knowledge to project repositories, shared OKF tooling and ecosystem knowledge to the dedicated knowledge repository, and deployment to infrastructure repositories. The companion introduces a Hermes profile, skill, MCP configuration, and authorization policy, but **confirmed** does not assign those durable artifacts to a repository or defer the decision.

The parent requires both project attestations and an ecosystem run for an ecosystem result. The Hermes workflow only invokes a project-owned harness, so **confirmed** there is no handoff to the ecosystem orchestrator when verification discovery returns ecosystem scenarios.

The parent separates receipt normalization, signing, signature verification, evaluation, and evidence proposal. The companion routes a worker receipt to the MCP server to “evaluate and attest,” so **confirmed** the signing principal and workload identity are undefined and the diagram conflicts with the later requirement that required receipts already be attested.

`regenerate_indexes` can update Git-tracked `index.md`, but neither document maps it to an authorization role. Because the companion disables automatic OKF writes while granting Hermes this tool, **confirmed** it is unclear whether this is cache maintenance, a draft proposal, or a canonical write.

## Hermes profile and skill have no repository owner

The companion makes the profile and `okf-software-development` skill known architecture (`docs/HERMES-FEDERATED-OKF-INTEGRATION.md:40`, `:94`, `:537-552`), but its recovery table only says “Profile export or configuration repository” (`:527`). The parent responsibility map has no owner for Hermes profile instructions, skills, MCP client configuration, or authorization policy (`docs/FEDERATED-OKF-KNOWLEDGE-AND-VERIFICATION-PROPOSAL.md:1202-1216`). **Confirmed:** assign these artifacts to the Hermes, dedicated knowledge, or deployment/configuration repository, distinguishing reusable source from environment-specific state.

## Ecosystem targets stop at detection instead of execution

The parent gives ecosystem E2E its own orchestrator and requires both conforming project evidence and ecosystem scenarios against exact composed revisions (`docs/FEDERATED-OKF-KNOWLEDGE-AND-VERIFICATION-PROPOSAL.md:160`, `:795-801`). The companion can discover ecosystem targets and treats missing ecosystem evidence as unverified, but only says Hermes invokes the project-owned harness (`docs/HERMES-FEDERATED-OKF-INTEGRATION.md:335-346`). **Confirmed:** add scope selection and an authorized handoff to the ecosystem runner, including how its result rejoins task completion.

## MCP is shown creating trust it is supposed to verify

The parent separates receipt generation from authenticity and requires a signed envelope backed by a CI or remote-runner workload identity (`docs/FEDERATED-OKF-KNOWLEDGE-AND-VERIFICATION-PROPOSAL.md:591-635`). The companion shows `Receipt -->|evaluate and attest| OKFMCP` (`docs/HERMES-FEDERATED-OKF-INTEGRATION.md:139-142`), while rejecting required receipts that are unattested (`:339-346`) and accepting evidence only after attestation policy passes (`:227`). **Confirmed:** define the worker/CI or a separate signing service as the signer and make MCP verify/evaluate the signed receipt, or explicitly define a separate MCP signing identity and trust boundary.

## Index regeneration crosses a canonical-write boundary without a role

The parent says `regenerate_indexes` updates `index.md` and derived manifests (`docs/FEDERATED-OKF-KNOWLEDGE-AND-VERIFICATION-PROPOSAL.md:878`) but grants no role that operation (`:905-909`). The companion exposes it to Hermes (`docs/HERMES-FEDERATED-OKF-INTEGRATION.md:228`) while disabling automatic OKF writes (`:191-194`) and assigning explicit roles to other mutations (`:478-481`). **Confirmed:** split disposable cache rebuilding from Git-tracked generated-file proposals; grant the former an operational permission and require draft-writer plus repository review for the latter.
